### ⚠️ 알려진 잔여 UX (버그 아님, 필요 시 다듬기)
- 같은 기기라도 **새 세션(새 탭/다음날)** 첫 로그인 시 충돌 창이 1회 뜰 수 있음 — 앱 로딩 시 습관 시드 등 정규화가 로컬을 미세 변형시켜 클라우드와 "다름"으로 잡히기 때문. 무한 반복은 수정됨(세션당 1회 제한). 거슬리면 정규화-차이 무시 로직 추가 검토.
- **충돌 선택 = 되돌리기 없는 전체 덮어쓰기** (미수정, 2026-07-24 점검서 식별). 충돌 창에서 한쪽 선택 시 반대쪽 데이터가 통째로 소멸하며 병합·백업·되돌리기가 없다. B+ 설계상 의도된 동작이나, 오클릭 시 유실이 크므로 덮어쓰기 직전 반대쪽 임시 스냅샷(되돌리기 여지) 추가를 향후 검토.

## ⚠️ 순환 의존 — Phase 3는 출시를 사이에 두고 쪼개진다

"Phase 3 전부 완료 → 출시"는 **물리적으로 불가능**하다. §4(결제)의 인앱 상품 등록은 **Play Console에 앱이 생성돼 있어야** 가능하므로, **출시가 결제의 선행 조건**이다.

**2026-07-28 갱신:** 쪼개지는 지점이 하나 더 있다. **§3 알림도 하이브리드 셸이 선행 조건**이다(웹은 앱이 닫히면 안 울림 → §3 서두 참조).

```
§P 사전준비 → §1 로그인 → §2 동기화               ← [출시 전]
        ↓
[하이브리드 셸 — Capacitor 도입]                   ← A-2. Android 셸 생성 완료(2026-07-28)
        ↓
§3 알림 (플랜 블록 기반 · 로컬 알림)                ← 셸 위에서만 만들고 검증 가능
        ↓
[출시 — docs/하이브리드-출시-할일.md A·B단계 (Android 비공개 + iOS TestFlight)]  ← 양 스토어에 앱 생성
        ↓
§4 결제 구현·검증                                  ← [출시 후] 여기서만 가능
        ↓
[테스터 12명×14일 → 공개 출시 + 실결제 개시]
        ↓
§5 배포 시 갱신 의무
```

**의도 보존:** 공개 출시 시점엔 §2가 끝나 **데이터 유실 문제가 없다.** 이것이 "Phase 3 먼저" 결정의 목적이었다(`docs/로드맵.md`).

- [ ] ☐ **1-11 App Check 도입 → 계정 존재 안내 개방** (2026-07-27 결정)

  **왜:** 로그인·재설정 등 인증 요청은 로그인 없이 누구나 보낼 수 있어, 응답 차이로 **어떤 이메일이 swithme에 가입돼 있는지**가 새어나갈 수 있다. (**2026-07-27 갱신:** 가입 경로 유출은 사라졌다 — 회원가입이 이메일 링크 방식이라 가입 여부와 무관하게 응답이 같다. 남은 건 열거 보호가 가리고 있는 나머지 경로다.) 자동 반복하면 가입자 이메일 명단이 만들어지고, 표적 피싱·크리덴셜 스터핑의 조준경이 된다. **§4 결제가 붙으면 피해 기대값이 올라가므로 결제 전에 막는다.** App Check는 어차피 결제 검증에도 필요해 두 번 일하지 않는다.

  **무엇:** 요청마다 "정상 앱에서 나왔다"는 단기 토큰을 붙이게 하고 없으면 Firebase가 거절. 발급처는 웹=reCAPTCHA, Android=Play Integrity, iOS=App Attest.

  **한계 (과신 금지):** 공격자가 자기 기기의 정품 앱에서 토큰을 뽑아 재사용하는 건 완전히 막지 못한다(클라이언트 검증의 근본 한계). 목표는 절대 차단이 아니라 **대량 자동화를 비경제적으로 만드는 것**. 또한 "특정 이용자만 골라 차단"은 App Check 기본 기능이 아니다 — 필요하면 서버 코드(Cloud Functions)로 직접 만들어야 한다.

  **단계:**
  - [ ] ☐ **1-11-a (유저)** Firebase 콘솔에서 App Check 등록 + reCAPTCHA 사이트 키 발급, **허용 도메인에 `swithme.app` 등록** (구글 로그인 승인 도메인과 같은 함정 — 누락 시 전 유저 차단)
  - [ ] ☐ **1-11-b** 웹 앱에 App Check 연동 + 개발용 디버그 토큰 등록 (미등록 시 로컬 테스트 전부 실패). 디버그 토큰은 불필요해지면 삭제 — 방치하면 우회로가 된다
  - [ ] ☐ **1-11-c** **모니터링 모드로 최소 며칠~1주 관찰** — 차단 없이 통과율만 수집. 구버전 앱·특이 브라우저·회사망에서 토큰 발급이 실패할 수 있어, 바로 강제하면 실유저가 로그인 자체를 못 한다
  - [ ] ☐ **1-11-d** 통과율 안정 후 **서비스별 순차 강제** — Auth 먼저 → 이상 없으면 Firestore. 한 번에 켜면 원인 분리가 안 된다. 문제 시 즉시 해제 가능(되돌리기 쉬운 변경)
  - [ ] ☐ **1-11-e (유저)** 강제 전환 후 실기기에서 로그인·동기화 정상 확인 — **자동화 불가, 이거 없이 "됐다" 판정 금지**
  - [ ] ☐ **1-11-f** 그 뒤 **이메일 열거 보호 해제** → 이미 구현된 "가입된 계정이 없어요" 안내 팝업 활성 + 재설정 성공 문구를 조건부("있다면 도착합니다")에서 단정("보냈어요")으로 교체

  > **대기 중인 코드:** 미가입 메일 재설정 시 회원가입을 유도하는 팝업은 이미 구현·커밋됨(64f9615). 열거 보호가 켜져 있는 동안 Firebase가 미가입 사실을 알려주지 않아 **실행되지 않는 대기 상태**다. 1-11-f에서 살아난다. 지우지 말 것.

  > **앱 출시 시 재작업:** 지금 붙이는 건 웹(reCAPTCHA) 경로뿐이다. Capacitor로 Android·iOS를 내면 Play Integrity·App Attest 경로를 각각 추가 등록해야 한다(`docs/하이브리드-출시-할일.md` 연동 시점).

  > **감수 결정:** App Check 도입 전까지 계정 존재 유출은 **감수한다**(2026-07-27). 현재 유저 수가 적고 결제·개인 식별 정보가 없어 피해 기대값이 낮다. **뒤집는 조건 — §4 결제 착수, 또는 유저 수 수천 명대 도달.** 둘 중 먼저 오는 시점에 1-11을 선행 조건으로 올린다.

## 3. 알림 — 플랜 블록 기반 — **[하이브리드 셸 이후]** (2026-07-28 규격·순서 변경)

> **⚠️ 순환 의존 2 (2026-07-28 식별).** §3은 그동안 "[출시 전]"으로 적혀 있었으나 완료 조건(실기기 수신 확인)이 하이브리드 셸을 요구했다. 더 근본적으로, **웹에서는 앱이 닫혀 있으면 알림이 뜨지 않는다** — 알림은 앱을 안 보고 있을 때 울려야 의미가 있으므로 웹만으로 만들면 기능의 목적 자체가 성립하지 않는다. §4 결제와 같은 유형의 순환 의존이며, **셸(Capacitor) 이후로 이동**한다.

> **규격 변경 (2026-07-28).**
> - **폐기:** 유저가 알림 시각을 직접 입력하는 "할 일 리마인더 / 습관 리마인더".
> - **채택:** **플랜 탭에 그려 둔 시간 블록 기반 알림.**
> - **이유:** 유저는 이미 플랜에 시간을 그려 놨다. 알림 시각을 또 입력받는 것은 같은 정보를 두 번 받는 것이다. 블록 기반이면 플랜을 그리는 순간 알림이 자동으로 따라오고, 습관도 플랜 탭에 블록으로 시드되므로 별도 항목 없이 자동 포함된다.

### 3-A. 확정 규격

- **알림 시점** = 블록 시작 시각. 유저가 고르는 것은 **정각 / 5분 전 / 10분 전**뿐이며 시각 입력은 없다.
- **알림 문구** = 그 블록의 카테고리·할 일 이름.
- **설정 위치** = 설정의 새 **"알림" 탭** (PC·모바일 양쪽 셸).
- **발송 방식 = 기기 로컬 알림.** 예약 시각을 기기가 기억하므로 서버가 필요 없다 → Firebase 무료 플랜(§P-4) 유지, 오프라인에서도 동작, iOS도 정상.
- ~~원격 푸시(FCM·APNs)~~ 는 **리마인더 용도에서 폐기.** 원격 푸시는 "누구에게 언제 보낼지 정하는 서버"를 요구해 유료 플랜(카드 등록)이 필요한데, 개인 일정 알림에는 이점이 없다. 공지·마케팅 일괄 발송이 실제로 필요해지는 시점에 별도 항목으로 신설한다.

> **부수 효과:** Apple은 웹뷰 단순 래핑 앱을 엄격히 본다(Review Guideline 4.2). 네이티브 알림 통합이 거절 방어가 된다(`docs/하이브리드-출시-할일.md` §1-2).

### 3-B. 미정 — 착수 전 유저 결정 필요

- ☐ **알림 기준 플랜 탭.** 플랜 탭은 여러 개 만들 수 있다. ① **현재 보고 있는 탭 하나**(추천 — 여러 탭을 합치면 같은 시간대 알림이 겹쳐 울린다) ② 모든 플랜 탭 합산. **2026-07-28 현재 미결.**

## 4. 결제 (토큰제 Freemium — **실결제**) — **[출시 후]**

> 근거 PRD §9-7(BM 확정) · §9-6(실결제). **선행 조건 두 가지:**
> 1. **비공개 테스트 출시 완료** — 인앱 상품 등록은 스토어에 앱이 있어야 가능(위 순환 의존)
> 2. **`docs/하이브리드-출시-할일.md` D단계** (사업자·통신판매업 확인, 판매자 등록, 환불 방침, 연락처). D-1 답 없이 실결제 착수 금지
>
> **상품 구성 (PRD §9-7):** ①구독(월/년, subscription) ②토큰팩(개수별, consumable) ③보상형 광고(AdMob). 분석 기능이 토큰 소비처. 각 상품 **최저가**(규모 완화 유지).

### 4-A. 토큰 시스템 (앱 내부 로직) — ✅ 구현 완료 (2026-07-28), **게이팅 스위치 OFF 상태**

>
> **⚠️ 원칙적으로 이 스위치는 꺼져 있어야 한다.** 획득 라인(광고·구독·토큰팩)이 스토어 출시 후에야 열리므로, 지금 켜면 분석이 월 1회로 잠긴다. 지급·병합·저장은 스위치와 무관하게 항상 돌아가므로 켜는 순간 유저는 그동안 쌓인 무료 사탕을 그대로 가지고 시작한다.

- [x] ✅ **4-1** 사탕 잔량을 로컬 저장 + 클라우드 문서에 함께 저장. 무료분/구매분 분리 보관, 기기 간 동기화 포함
- [x] ✅ **4-2** 분석 기능 **사탕 게이팅** — 기간별 가격표(PRD §9-7). 잔량 부족 시 획득 안내 팝업(광고·구독·토큰팩 = "준비 중" 표기)
- [x] ✅ **4-3** 획득/차감 로직 + 잔량 배지(PC·모바일 양쪽). 무료분 우선 차감. 같은 날 같은 기간 재조회는 무료
- [x] ✅ **4-3b** **매달 무료 사탕 1개 자동 지급** — 전 유저, 같은 달 중복 지급 차단(지급월 기록)

- [x] ✅ **4-3d** 유닛테스트 17건(가격표·월 지급 멱등·차감 우선순위·이관 규칙·값 보정)
