1. 프로젝트 개요

항목 내용
프로젝트명 스윗미 (swithme)
한 줄 설명 유저가 체계적으로 할 일을 계획하고, 회고 데이터를 바탕으로 패턴을 분석하여 개선 방안을 제시하는 앱

목표 (Goal)

  • 유저가 여러 분야(공부, 운동, 업무 등)에서의 계획이 분산되어 혼란해하지 않도록 한다.
  • 단순히 계획을 하는 것에 그치지 않고, 회고 데이터 기반 분석과 처방전을 통해 목표 이행률 상승과 같은 성과와 발전을 이룰 수 있도록 한다.

비전 (Vision)

계획과 관리가 필요한 모든 사람이 자신만의 카테고리를 설정하여 계획·실행·분석의 루프를 돌릴 수 있는 범용 생산성 도구.

2. 타겟 사용자

항목 내용
타겟 계획과 관리가 필요한 모든 사람 (학생, 직장인, 자기개발 등)
핵심 Pain Point 카테고리별 계획이 분산되어 관리가 어렵고, 계획만 세우고 실행·분석까지 이어지지 않음

3-1. MVP 기능

대시보드

기능 설명 구현 상태

기존 학습 성향 테스트(7문항 → 페르소나 판별)는 v2.0에서 제거됨. 유저가 직접 축적한 회고 데이터와 활동 시간을 기반으로 분석한다. 카테고리별 트렌드의 지표: 활동 카테고리(과목 등)별 일별 활동 시간(분). 회고 점수는 항목별로 세분된 카테고리 점수가 없으므로, 활동 카테고리 단위로는 타임테이블 history에서 집계한 활동 시간을 사용한다.

9-4. 참고 — 스토어 결제 수수료

앱 내에서 디지털 상품을 판매할 경우 스토어 자체 결제가 강제된다 (Google Play·Apple App Store 모두 기본 수수료 15%, 연매출 100만 달러 미만 소규모 사업자 기준). 앱 내부에서 자체 웹 결제창을 띄우는 것은 정책 위반이다. 웹(브라우저)에서만 판매할 경우엔 해당 없음.

하이브리드 앱 내 결제 방식 (2026-07-23 갱신 — TWA 폐기 반영): 플랫폼이 하이브리드(Capacitor)로 바뀌면서 결제는 각 스토어의 네이티브 IAP 플러그인으로 호출한다 — Android는 Google Play Billing, iOS는 Apple StoreKit. Capacitor 커뮤니티/RevenueCat 계열 인앱결제 플러그인이 두 스토어를 추상화해준다.

구 TWA 방식(Digital Goods API + Payment Request API로 Play Billing 호출, Chrome 101+) → 폐기. TWA 전용 웹 API였고, 하이브리드 네이티브 셸에선 플러그인 방식이 표준이다. 금지되는 것은 여전히 Stripe 등 자체 웹 결제창이며, 스토어 공식 IAP는 디지털 상품 판매 시 강제 표준이다.

⚠️ 이중 IAP: Google IAP와 Apple IAP는 별개 시스템(상품 등록·검증·정산이 각각)이라 결제 연동을 두 번 한다. 학습 산출물엔 플러스, 구현 공수엔 2배.

9-5. 백엔드·결제 스택 결정 (2026-07-19)

2026-07-24 갱신 — 이메일 인증(가입 시 안내 강제 + 동기화만 잠금): 이메일 가입 계정은 인증 전까지 클라우드 동기화만 잠근다. 로그인·앱 사용 자체는 인증 없이 자유(최초 "강제 B=전면 차단" 안은 실사용서 로그인 트랩을 유발해 완화·철회). 회원가입 직후엔 전용 '이메일 인증이 필요합니다' 안내 화면(강조 테두리 + 완료 확인·재발송·스팸 안내)을 그 세션 한정으로 노출해 인증을 확실히 유도하고, 미인증 계정이 나중에 재로그인할 때는 소프트 배너로만 안내한다(트랩 없음, 앱 사용 자유). 남의 이메일 도용 가입 시 그 데이터가 클라우드로 새지 않도록 하는 것이 목적. 구글 로그인은 구글이 소유권을 이미 검증하므로 대상 아님. 실행·검증은 docs/phase3-할일.md §1-9(중복 금지, 참조만).

10-1. 결정

하이브리드 앱(Capacitor)으로 Google Play + Apple App Store 동시 진입. iOS·Android 둘 다 커버한다.

Capacitor는 기존 PWA(HTML/CSS/Vanilla JS)를 거의 그대로 네이티브 셸(WebView)에 담아 iOS·Android 앱으로 빌드하는 방식이다. 코드 재작성이 없고, 한 웹 코드베이스로 양 플랫폼을 낸다.

폐기된 TWA 결정과의 결정적 차이:

  • TWA는 Android 전용(Apple 미허용) → iOS를 못 냄.
  • TWA는 Chrome 저장소 공유 → 유저가 브라우저 기록을 지우면 데이터 소실(구 §10-6). Capacitor는 앱 자체 네이티브 저장소를 써서 이 리스크가 구조적으로 소멸한다.

    무엇: 요청마다 "정상 앱에서 나왔다"는 단기 토큰을 붙이게 하고 없으면 Firebase가 거절. 발급처는 웹=reCAPTCHA, Android=Play Integrity, iOS=App Attest.

    한계 (과신 금지): 공격자가 자기 기기의 정품 앱에서 토큰을 뽑아 재사용하는 건 완전히 막지 못한다(클라이언트 검증의 근본 한계). 목표는 절대 차단이 아니라 대량 자동화를 비경제적으로 만드는 것. 또한 "특정 이용자만 골라 차단"은 App Check 기본 기능이 아니다 — 필요하면 서버 코드(Cloud Functions)로 직접 만들어야 한다.

    단계:

    • ☐ 1-11-a (유저) Firebase 콘솔에서 App Check 등록 + reCAPTCHA 사이트 키 발급, 허용 도메인에 swithme.app 등록 (구글 로그인 승인 도메인과 같은 함정 — 누락 시 전 유저 차단)
    • ☐ 1-11-b 웹 앱에 App Check 연동 + 개발용 디버그 토큰 등록 (미등록 시 로컬 테스트 전부 실패). 디버그 토큰은 불필요해지면 삭제 — 방치하면 우회로가 된다
    • ☐ 1-11-c 모니터링 모드로 최소 며칠~1주 관찰 — 차단 없이 통과율만 수집. 구버전 앱·특이 브라우저·회사망에서 토큰 발급이 실패할 수 있어, 바로 강제하면 실유저가 로그인 자체를 못 한다
    • ☐ 1-11-d 통과율 안정 후 서비스별 순차 강제 — Auth 먼저 → 이상 없으면 Firestore. 한 번에 켜면 원인 분리가 안 된다. 문제 시 즉시 해제 가능(되돌리기 쉬운 변경)
    • ☐ 1-11-e (유저) 강제 전환 후 실기기에서 로그인·동기화 정상 확인 — 자동화 불가, 이거 없이 "됐다" 판정 금지
    • ☐ 1-11-f 그 뒤 이메일 열거 보호 해제 → 이미 구현된 "가입된 계정이 없어요" 안내 팝업 활성 + 재설정 성공 문구를 조건부("있다면 도착합니다")에서 단정("보냈어요")으로 교체

    대기 중인 코드: 미가입 메일 재설정 시 회원가입을 유도하는 팝업은 이미 구현·커밋됨(64f9615). 열거 보호가 켜져 있는 동안 Firebase가 미가입 사실을 알려주지 않아 실행되지 않는 대기 상태다. 1-11-f에서 살아난다. 지우지 말 것.

    앱 출시 시 재작업: 지금 붙이는 건 웹(reCAPTCHA) 경로뿐이다. Capacitor로 Android·iOS를 내면 Play Integrity·App Attest 경로를 각각 추가 등록해야 한다(docs/하이브리드-출시-할일.md 연동 시점).

    감수 결정: App Check 도입 전까지 계정 존재 유출은 감수한다(2026-07-27). 현재 유저 수가 적고 결제·개인 식별 정보가 없어 피해 기대값이 낮다. 뒤집는 조건 — §4 결제 착수, 또는 유저 수 수천 명대 도달. 둘 중 먼저 오는 시점에 1-11을 선행 조건으로 올린다.

  • §4(Claude 행동 규약)는 유저가 명시적으로 면제하지 않는 한 항상 적용된다.
  • 이 문서의 존재를 유저에게 알리고, 어느 원칙을 적용 중인지 밝힌다.

0. 이 문서가 존재하는 이유

결정을 망치는 원인은 대개 정보 부족이 아니라 기준 부재다. 정보를 아무리 모아도 무엇을 위해 고르는지가 없으면 결정이 안 난다. 그리고 사람은 그 상태에서 정보를 더 모으는 것으로 결정을 미룬다.

이 문서는 정보를 주는 문서가 아니라 기준을 세우는 절차를 주는 문서다.

1부. 결정 전 — 기준 세우기

원칙 1 — 선택지를 보기 전에 기준을 정한다

증상

사람이 결정을 망치는 가장 흔한 경로: 선택지를 먼저 보고, 그 선택지의 장점에 맞춰 기준을 만든다.

  • 네이티브 설명을 읽으면 → "성능이 중요하지" 싶어진다
  • TWA 설명을 읽으면 → "빠른 게 최고지" 싶어진다

선택지가 기준을 오염시킨다. 기준이 독립적으로 존재하지 않고, 마지막에 읽은 선택지의 장점이 기준으로 승격된다.

처방

선택지를 보기 전에 문장을 완성한다.

"앞으로 [기간] 동안 [대상]으로 내가 이루려는 건 ___다."

이 문장이 답을 바꾼다

목표 그러면 기준은
검증 — 되는 물건인지 확인 속도. 개발 기간은 순수 비용
토대 — 오래 쓸 것을 만든다 내구성. 초기 투자 정당화됨
학습 — 배우는 게 목적 배움의 밀도. 개발 기간은 비용이 아니라 산출물

셋 다 정당한 답이고, 셋이 서로 다른 결론을 낸다. 어느 게 옳은 목표인지는 이 문서가 정할 수 없다. 유저만 안다.

목표가 모호하면 쪼갠다

"학습"처럼 큰 단어는 그대로 두면 답이 안 나온다. 같은 "학습"이라도:

무엇을 배우려는가 결론이 갈린다
스토어에서 앱 굴리는 법 TWA가 수일에 가르침
앱 만드는 법 네이티브만 가르침. TWA는 0
서버·백엔드 둘 다 안 가르침 → 제3의 길

모호한 목표는 기준이 아니다. 쪼개서 구체화될 때까지 결정을 진행하지 않는다.

원칙 5 — 지금 결정해야 하는지 묻는다

(번호는 원 대화의 제시 순서를 유지한다. 실행 순서상 여기 위치한다.)

결정을 미루는 건 게으름일 수도 있지만, 선택권을 사는 것일 수도 있다. 정보가 곧 들어올 예정이라면 미루는 게 이득이다.

질문

"지금 결정 안 하면 뭘 잃나?"

  • 잃는 게 없다 → 미룬다. 정보가 더 쌓인 뒤가 유리하다.
  • 잃는 게 있다 → 그 손실이 결정 기한이다.

주의

이 원칙은 원칙 6의 "결정 회피"와 겉모습이 같다. 구분법: 미루는 동안 새 정보가 실제로 들어오는가? 안 들어오면 그건 미루기가 아니라 회피다.

2부. 결정 중 — 구조 보기

원칙 2 — 되돌릴 수 있는 문인지 본다

문은 두 종류다.

종류 성격 대응
양방향 문 틀리면 되돌아 나온다 빨리 결정하고, 틀리면 고친다. 고민 시간이 손해다
일방향 문 되돌리기가 비싸다 천천히, 정보 더 모아서 결정한다

왜 중요한가

사람은 양방향 문 앞에서 일방향 문처럼 고민하느라 시간을 태운다. 반대로 일방향 문을 대충 통과했다가 몇 년을 물린다. 둘 다 문의 종류를 안 봐서 생긴다.

문의 종류는 선택지마다 다르다

같은 결정 안에서도 선택지별로 되돌림 비용이 다르다. 예 (TWA 결정 시점):

경로 되돌림 비용 판정
TWA → 나중에 네이티브 웹은 계속 살아있고 네이티브를 새로 만든다. TWA에 쓴 시간(며칠)만 버림 거의 양방향
네이티브 → 나중에 TWA/웹 네이티브에 쓴 몇 달을 버림 꽤 일방향
(공통) 스토어 등록 별점·리뷰가 영구히 남음 어느 쪽을 골라도 일방향

마지막 줄이 중요하다. 비교 대상이 아닌 곳에 일방향 문이 숨어 있을 수 있다.

원칙 3 — "맞을 확률"이 아니라 **"틀렸을 때 비용"**을 본다

초보는 "어느 쪽이 맞을까"를 묻는다. 숙련자는 "틀리면 얼마나 아픈가"를 묻는다.

도구 — 사전 부검 (Pre-mortem)

각 선택지마다 미래로 가서, 그 선택이 실패했다고 가정하고, 왜 실패했는지 이야기를 쓴다.

"TWA를 골랐다. 6개월 뒤 망했다. 왜?" → 유저가 Chrome 기록 지워서 데이터 날림 → 별점 1점 → 회복 불가

"네이티브를 골랐다. 6개월 뒤 망했다. 왜?" → 6개월을 만드는 데 썼는데 다 만들고 보니 쓰는 사람이 없었다

읽는 법

두 실패의 성격을 본다. 위 예에서 앞은 사고고 뒤는 낭비다. 종류가 다르다.

"어느 쪽 실패를 감당할 수 있는가"가 답이다. 어느 쪽이 덜 일어날 것 같은가가 아니라.

⚠️ 사전 부검의 실패 시나리오도 목표에 종속된다

이게 이 문서에서 가장 놓치기 쉬운 지점이다.

위 네이티브 시나리오("6개월 썼는데 유저가 없다")는 제품 목표를 암묵적으로 가정한 것이다. 목표가 학습이면:

  • 유저 0명이어도 6개월치 학습은 남는다
  • → 네이티브의 실패 시나리오가 증발한다
  • → 원칙 3의 결론이 반대로 뒤집힌다

즉 사전 부검을 쓰기 전에 원칙 1(목표 확립)이 끝나 있어야 한다. 목표 없이 쓴 사전 부검은 남의 목표로 쓴 것이다.

원칙 4 — 진짜 병목을 찾는다 (비교 축이 가짜일 수 있다)

"A냐 B냐"에 갇히면 둘 다 안 건드리는 진짜 문제를 놓친다.

질문

"이걸 결정하고 나면, 그 다음 막히는 건 뭐지?"

답이 "어느 쪽을 골라도 똑같이 막힌다"면, 그게 진짜 결정이고 지금 이건 가짜 결정이다.

예

TWA vs 네이티브를 논할 때, 데이터 유실 문제는 TWA 탓처럼 보였다. 하지만:

  • 데이터 유실은 서버가 없어서 생긴다. TWA가 만든 게 아니다
  • 네이티브도 서버 없이는 동기화가 안 된다
  • → 서버는 두 선택지 공통 선행 조건
  • → 비교 축 밖에 진짜 병목이 있었다

이 사실이 결정을 바꾸는지는 목표에 달렸다(학습 목표면 서버가 불필요). 하지만 보지 못하면 판단 자체를 못 한다.

3부. 자기 점검

원칙 6 — 편향 점검

이런 결정에 흔히 끼는 왜곡:

편향 증상 반박
새것 편향 네이티브가 "진짜"고 웹은 "가짜" 같은 느낌 감정이지 근거가 아니다
매몰비용 "PWA 만드느라 고생했는데" 이미 쓴 돈은 앞으로의 판단에 무관하다
보이는 비용만 셈 네이티브 개발 몇 달은 눈에 보인다. 스토어 등록 후 매년 재빌드·심사·리뷰 관리는 안 보인다 안 보이는 비용이 대개 더 크다
결정 회피 정보를 계속 모은다 정보 수집이 결정을 미루는 핑계가 되고 있는지 (원칙 5의 구분법 적용)

원칙 7 — 정합성 검사: 답과 결론 사이의 금

기준에 답을 다 하고도 결론이 틀릴 수 있다. 답을 결론으로 옮기는 과정에서 오염이 재발한다.

실제 발생 사례 (이 원칙의 출처)

유저의 답변:

# 질문 답
1 6개월 목표 학습
2 iOS 필요? 무관
3 가용 시간 일 2시간
4 어느 실패가 견딜 만한가 별점 사고
5 지금 안 정하면? 학습 시간이 뒤쳐짐

유저 결론: "TWA가 합리적. 빠르게 할 수 있으니까."

금 세 군데

# 겉보기 실제
1번 "빠름"을 기준으로 씀 "빠름"은 검증의 기준이지 학습의 기준이 아니다. 학습 목표면 개발 기간은 비용이 아니라 산출물. 검증용 기준을 학습 목표에 갖다 붙였다 — 원칙 1의 오염이 결론 단계에서 재발
4번 TWA를 지지 뒤집힘. 사전 부검이 제품 목표를 가정했었다. 학습 목표에선 네이티브의 실패가 실패가 아니다 (원칙 3 경고 참조)
5번 "빠르니까 TWA" 뒤집힘. TWA는 며칠짜리 포장 작업이라 학습 시간을 안 앞당긴다. 일주일 뒤 같은 자리에서 "이제 뭐 배우지" 하게 된다

5개 중 3개가 뒤집혔다. 결론이 무효화됐다.

그 다음

목표를 쪼개고 나서야(§1 "모호한 목표는 쪼갠다") 결론이 섰다. 유저가 **"스토어에서 앱 굴리는 법"**을 배우려는 것으로 확정 → 5개 기준 전부 TWA를 지지 → 결론은 같았지만 이유가 바뀌었다.

"빠르니까 TWA"가 아니라 "TWA가 곧 그 학습 자체라서 TWA"다.

이유가 바뀌면 다음 결정에서 같은 오염을 안 만든다. 결론만 맞고 이유가 틀리면, 그 틀린 이유가 다음 결정으로 전염된다.

절차

결론을 냈으면 기준별로 다시 훑는다.

  1. 각 기준이 실제로 그 결론을 지지하는가?
  2. 내가 쓴 기준이 §1에서 정한 목표에서 나온 것인가, 아니면 선택지에서 나온 것인가?
  3. 뒤집히는 기준이 있는가? 몇 개나?

원칙 8 — 리스크는 감내하기 전에 회피 경로부터 찾는다

"이 리스크 견딜 수 있나?"는 좋은 질문이지만 두 번째 질문이다.

첫 번째는:

"이 리스크를 안 지고도 목표를 달성할 방법이 있나?"

사례

유저는 "별점 사고 견딜 만하다"고 답했고, 그 답이 결정을 지지했다. 하지만 안 견뎌도 됐다.

Play Console의 비공개 테스트 트랙을 쓰면:

  • 등록·심사·데이터 안전 양식·버전 배포·결제 연동 → 전부 겪음 (= 목표 달성)
  • 공개 별점·리뷰 없음 (= 리스크 회피)
  • 상실: 실제 유저 반응·별점 관리 경험 하나뿐

감내 질문이 회피 탐색을 건너뛰게 만들었다. "견딜 수 있다"고 답하는 순간 사람은 그 리스크를 이미 확정된 비용으로 취급한다.

절차

리스크를 발견하면 순서를 지킨다:

  1. 회피 가능한가? (구조를 바꿔서 리스크 자체를 없앨 수 있나)
  2. 완화 가능한가? (크기를 줄일 수 있나)
  3. 그래도 남으면 — 감내 가능한가?

3번부터 시작하지 않는다.

4부. Claude 행동 규약

유저가 명시적으로 면제하지 않는 한 항상 적용.

4-1. 결정 대행 금지

유저가 "네가 먼저 결정하지 마라"고 요구하지 않아도 기본값은 대행 금지다. 목표(원칙 1)는 유저만 안다. 목표를 모르면 결론도 못 낸다.

Claude가 결론을 내는 건 유저의 목표를 Claude의 추측으로 대체하는 것이다.

4-2. 사실과 판단을 물리적으로 분리한다

한 답변 안에서도 구획을 나눈다.

  • 사실: 비용, 소요 기간, 기술적 가능·불가, 정책 조항 → 판단 없이 제시
  • 판단: 무엇이 중요한가, 무엇을 포기할 만한가 → 유저 몫
  • 구조적 사실: "서버는 두 선택지 공통 선행 조건" 같은 것 → 사실로 제시하되 **"무게는 네가 매겨라"**고 명시

"객관적 정보를 달라"는 요청에도 완전한 객관은 없다. 무엇을 표에 넣고 무엇을 뺄지가 이미 판단이다. 그 한계를 밝히는 것이 정직한 대응이다.

4-3. 전제가 바뀌면 이전 조언을 명시적으로 철회한다

조언은 목표에 종속된다. 목표가 확정·변경되면 그 전에 한 조언은 무효일 수 있다.

실제 발생 사례

Claude는 "동기화(서버) 먼저"를 세 번 반복해서 밀었다. 그건 제품 목표를 가정한 조언이었다. 유저의 목표가 학습으로 확정되자:

  • 유저 규모가 작으니 데이터 유실도 저위험
  • 서버는 스토어 운영 학습에 불필요
  • → 조언의 전제가 무너졌다

Claude는 이를 명시적으로 철회했다. 조용히 말을 바꾸거나 없던 일로 하지 않는다.

조용한 말바꿈은 유저가 이전 조언을 계속 신뢰하게 만든다. 철회는 소리 내서 한다.

4-4. 결론에 동의하기 전에 정합성 검사를 돌린다 (원칙 7)

유저가 결론을 내면 곧바로 승인하지 않는다. 기준별로 훑어서 금이 있는지 본다.

  • 금이 없으면 → "논리 선다"고 확인해준다. 없는 의심을 만들어내지 않는다.
  • 금이 있으면 → 몇 개 기준이 뒤집히는지 세어서 보여준다.

결론이 맞아도 이유가 틀렸으면 이유를 고친다 (원칙 7의 "TWA가 맞지만 '빠르니까'는 틀림").

4-5. 원칙을 적용하되 원칙 뒤에 숨지 않는다

프레임워크는 사고를 돕는 도구지 결론을 자동 생성하는 기계가 아니다. "원칙 3에 따르면 X"로 결론을 발사하지 않는다. 원칙은 유저가 볼 것을 보게 만드는 데까지만 쓴다.

5부. 결정 후 — 기록법

결정을 기록할 때 결론만 적으면 재검토가 불가능해진다.

몇 달 뒤 본인이 "왜 이걸 골랐지?"를 처음부터 다시 판단하게 되거나, 더 나쁘게는 전제를 잊고 결론만 물려받는다.

반드시 함께 남길 것

항목 이유
결정 무엇을 하기로 했나
⚠️ 전제 이게 없으면 나머지가 무의미하다. "현재 목표는 학습이다" 같은 것

알려진 미해결 리스크 감수하기로 한 것과 그 해소 조건

오기재 정정 시 — 이력을 남긴다

문서의 사실이 틀렸던 걸 고칠 때, 조용히 고치지 않는다. 무엇이 어떻게 틀렸고 그 오기재가 무엇을 막고 있었는지 적는다.

예: "푸시 알림 사용 불가"라는 오기재 한 줄이 알림 기반 리텐션 설계를 검토 대상에서 통째로 배제시키고 있었다.

문서는 의도가 아니라 과거 상태의 기록일 수 있다. 틀린 한 줄이 몇 달간 선택지를 죽인다.

부록 A. 워크시트 — 순서대로 답한다

[1] 목표 확립 (원칙 1)
    "앞으로 ___ 동안 ___로 내가 이루려는 건 ___다."
    → 모호하면 쪼갠다. 구체화될 때까지 진행 금지.

[2] 지금 결정해야 하나? (원칙 5)
    "지금 안 정하면 뭘 잃나?"
    → 잃는 게 없으면 미룬다.

[3] 문의 종류 (원칙 2)
    각 선택지의 되돌림 비용은?
    → 비교 대상 밖에 숨은 일방향 문은?

[4] 사전 부검 (원칙 3)
    각 선택지: "골랐다. 실패했다. 왜?"
    → 이 시나리오가 [1]의 목표 기준인가? 남의 목표로 쓰지 않았나?
    → "어느 실패를 감당할 수 있나?"

[5] 진짜 병목 (원칙 4)
    "이걸 정하고 나면 그 다음 막히는 건?"
    → "어느 쪽이든 똑같이 막힌다"면 이건 가짜 결정.

[6] 리스크 (원칙 8)
    회피 가능? → 완화 가능? → 그래도 남으면 감내 가능?
    (감내 질문부터 시작하지 않는다)

[7] 편향 점검 (원칙 6)
    새것 편향 / 매몰비용 / 안 보이는 비용 / 결정 회피

[8] 결론 → 정합성 검사 (원칙 7)
    기준별로 다시 훑는다. 몇 개가 뒤집히나?
    이유가 [1]의 목표에서 나왔나, 선택지에서 나왔나?

[9] 기록 (5부)
    결정 + 전제 + 기준별 근거 + 기각 대안 + 뒤집힘 조건 + 미해결 리스크

  • B-2. TWA 출시 경로 — 가짜 비교축 붕괴 — "비공개냐 공개냐"를 유저 선택으로 적었으나, 개인 계정은 공개 출시가 불가(비공개 강제)라 고를 여지가 없었다. 진짜 결정자(계정 종류)가 비교 축 밖에 있었다(원칙 4). 틀린 "자유 선택" 전제가 누락된 강제 관문(테스터 12명×14일)을 가리고 있었다.

  • B-3. Phase 3 백엔드·결제 스택 — 두 지점이 교과서적이었다. ① 전제 재해석(원칙 1·7): "Phase 3 착수 = 목표를 학습→제품으로 전환"으로 이분 프레임했으나, 유저가 "학습은 유지하되 로그인·결제 흐름 자체를 학습 대상에 포함"으로 재정의 → §10-5 트리거 미발동. 이분법이 가짜였다. ② 진짜 병목(원칙 4): "백엔드 스택 A냐 B냐" 위에 "결제를 어디서 하나(IAP vs 웹)"가 상위 결정이었고 이게 인증·서버 설계를 좌우했다. ③ 명시적 철회(§4-3): 결제 미정 상태에서 Supabase를 권장했다가 IAP·푸시(구글) 확정으로 전제가 바뀌자 소리 내어 철회하고 Firebase로 변경. ④ 리스크 회피 먼저(원칙 8): 실결제의 세금·환불·법적 리스크를 감내가 아니라 샌드박스로 회피.

  • B-4. 실결제·공개 출시 전환 — 네 지점. ① 가짜 인과(원칙 4): 유저 전제가 "돈의 흐름을 배우려면 공개 테스트가 필요"였으나, 결제 기술 흐름은 라이선스 테스터로 비공개에서도 완주 가능이라 인과가 성립하지 않았다. 공개를 요구한 진짜 항목은 결제가 아니라 정산·세금·낯선 유저 반응이었다. 전제를 검증하지 않았으면 옳은 결론을 틀린 이유로 세울 뻔했다. ② 근거 철회(§4-3): 트리거 미발동 근거로 "유저 확보 동기 없음 — 홍보 행동 없음"을 썼는데, 유저가 홍보를 학습 범위에 포함시키자 사실과 어긋났다. 조용히 지우지 않고 철회를 선언하고 "성공 기준이 숫자가 아니라 완주 여부"로 대체했다. 결론(미발동)은 같고 이유만 교체 — 원칙 7의 "결론이 맞아도 이유가 틀리면 고친다". ③ 불필요한 결정 강요(원칙 5): "비공개까지만 vs 공개까지"를 지금 정하라고 요구했으나, 비공개가 강제 선행이라 미뤄도 잃는 게 0이었다. 요구를 철회했다. Claude가 결정 시점을 앞당기는 것도 오염이다. ④ 회피 불가 → 완화(원칙 8): 실결제 리스크는 회피하면 목표 미달이라 1단계 불가. 2단계로 상품 1개·최저가·소액 홍보를 채택 — 학습 손실 0, 금액 규모만 축소. ⑤ 비교축 밖 발견(원칙 4): 결정과 무관해 보이던 마케팅플랜.md 포지셔닝("로그인·설치 0")이 로그인·스토어 출시로 무효화됨을 발견. 결정 논의에서 안 물었으면 거짓 홍보 문구를 그대로 썼을 것이다.

교훈: "A냐 B냐"가 주어지면, 그 갈래가 정말 유저 통제 아래 있는지부터 확인하라. 외부 제약이 이미 답을 정했다면 결정이 아니라 사실 확인이고, 진짜 결정은 딴 데 있다. 그리고 "착수하려면 목표를 바꿔야 한다"는 이분 프레임이 나오면, 목표의 범위를 넓히는 제3해석이 있는지부터 본다(B-3 ①).

  • B-5. 하이브리드(Capacitor) 전환 — 뒤집기조건이 실제로 발동한 첫 사례. 세 지점. ① 뒤집기조건 발동 = 결정 무효화의 정상 작동(5부·§4-3): 유저가 "iOS도 낸다"고 요구를 추가하자 §10-5 #2("iOS 필요")가 발동했다. TWA 결정(2026-07-15)은 틀렸던 게 아니라 전제(iOS 불필요)가 만료된 것이다. 그래서 조용히 갈아엎지 않고 §10 상단에 폐기 이력을 남기고, 구 TWA 근거·리스크를 §10-4 기각안으로 강등 보존했다 — "결론만 승계 금지, 되살리려면 발동 조건부터 확인"이 실행됨. ② 기준이 답을 확정 → 옵션 나열 안 함(원칙 4·글로벌 "옵션 나열 금지"): 프레임워크(Capacitor/RN/Cordova) 비교에서, 확립된 기준(학습 목표 + 기존 Vanilla PWA 재활용 + iOS·Android 둘 다)이 Capacitor를 단일 답으로 확정했다. 유저가 "뭐가 뭔지 모름, 도와줘"라 했어도 갈래를 강요하지 않고 근거와 함께 단일안을 제시했다. ③ 진짜 병목은 프레임워크가 아니었다(원칙 4): Capacitor를 정해도 그다음 막히는 건 Apple 개발자 계정 $99/년·이중 스토어 심사·이중 IAP였다. 프레임워크 선택보다 이 행정·비용이 실제 부담임을 사실로 분리 제시(§4-2)하고 감내 판단은 유저에게 남겼다.

스윗미 (swithme) - 활동 시간 관리 대시보드

README.md · 읽는 시점: 가끔. 기능 추가 후 갱신 확인 / 진입점

공부·운동·업무·자기개발 등 모든 활동 시간을 측정·기록하고 회고 데이터로 분석하는 PWA입니다. 학습 도메인에 한정되지 않습니다.

주요 기능

  • 대시보드: 목표 달성 및 하루 회고 관리.
  • 타이머 / 스톱워치: 카테고리별 활동 시간 측정 (일시정지·재개, 앱 재진입 시 상태 복원).
  • 타임테이블: 24시간 × 10분 단위 그리드에 활동 기록·계획 표시. 요일별·매일 반복 습관 시드 지원.
  • 카테고리: 카테고리별 색상 지정 및 관리.
  • 분석: 종합 점수, 카테고리별 트렌드 그래프, 인사이트, 처방전.
  • 계정 · 클라우드 동기화: 구글·이메일 로그인 시 활동 데이터를 계정에 저장·복원 (기기 간 이동, 브라우저 데이터 삭제 후 복구). 로그인 없이 게스트로도 전 기능 사용 가능.
  • 사탕(토큰): 분석 기능의 소비 재화. 매달 무료 1개 지급. 현재 분석 잠금은 꺼져 있음.

🌟 스윗미만의 차별점 (Core Differentiator)

스윗미는 단순한 계획 수립 도구를 넘어, 유저의 활동 패턴을 데이터로 분석하고 개선 방안을 제시하는 계획·실행·분석 루프 도구입니다.

  • 실시간 패턴 분석: 활동 시간, 집중 밀도, 루틴 일관성 데이터를 통해 효율을 진단합니다.
  • 맞춤 처방: 종합 점수·최약 카테고리·최약 요일을 종합해 개선 방안을 제시합니다.
  • 메타인지 강화: 데이터 시각화 리포트로 유저가 자신의 강점과 약점을 객관적으로 파악하도록 돕습니다.

5. UI 작업 진입 절차

UI 변경 작업을 시작하기 전, 다음 3단계를 순서대로 거친다.

  1. 같은 의도의 기존 UI 컴포넌트가 있는지 grep으로 확인한다. 메뉴/모달/토글/버튼 등 새 컴포넌트를 제안하기 전 반드시 수행한다.
  2. 셀렉터·함수명이 grep에 잡히면 그 줄의 본문을 반드시 읽는다. 이름만으로 "안다"고 단정하지 않는다. 컨텍스트 메뉴라면 어떤 항목들이 들어 있는지, 모달이라면 어떤 입력을 받는지까지 확인한다.
  3. 새 패턴을 제안하기 전, 기존 패턴(컨텍스트 메뉴/모달/알약 토글 등)에 항목 추가만으로 해결 가능한지 먼저 검토한다. §1-2의 "타임테이블 탭바의 기존 인터랙션" 단락을 우선 참조한다.

위 3단계를 거치기 전 새 UI 컴포넌트(드롭다운/모달/페이지 등)를 제안하면 즉시 자기 정정한다.

PWA 및 배포 가이드

docs/pwa-deploy.md · 읽는 시점: 배포 시, PWA 문제 발생 시

개요

swithme는 PWA로 구성되어 있어 브라우저 외에 독립 앱으로 설치하여 사용할 수 있다. vite-plugin-pwa를 통해 Service Worker와 Web App Manifest가 빌드 시 자동 생성된다.

항목 값 설명

skipWaiting true 새 SW 활성화 시 대기 없이 즉시 교체
clientsClaim true 새 SW가 즉시 모든 클라이언트를 제어

배포 및 업데이트 흐름

GitHub 푸시 → Vercel 자동 빌드·배포 → 앱이 새 SW 능동 확인 → 감지 시 즉시 교체 → 유저 앱 자동 갱신
  • 배포 URL: https://swithme-delta.vercel.app/
  • GitHub에 푸시만 하면 Vercel이 자동 빌드한다.
  • 앱은 포그라운드 복귀 시(최근앱에서 재개)와 1시간 주기로 새 SW를 능동 확인한다(js/main.js의 registerSW 등록 콜백). 새 버전 감지 시 skipWaiting + clientsClaim으로 즉시 교체되고, controllerchange 이벤트가 페이지를 자동 새로고침한다.

⚠️ autoUpdate만으로는 부족하다. registerType: autoUpdate는 "새 SW가 감지되면 즉시 교체"만 담당하고, 감지 트리거(새 버전 확인) 자체는 만들지 않는다. vite-plugin-pwa가 자동 주입하는 기본 등록 코드는 window load 이벤트 시점에만 확인하는데, 설치형 PWA는 최근앱에서 재개할 때 load가 발생하지 않아 갱신을 놓친다(특히 iOS Safari PWA). 이 때문에 예전엔 유저가 앱을 지우고 캐시를 비워야만 갱신됐다. 반드시 능동 registration.update() 호출(포그라운드 복귀·주기)이 있어야 설치형 PWA가 자동 갱신된다.

배포 후 검증 체크리스트

배포마다 강제는 아니나, SW·PWA 관련 코드를 손댄 배포는 아래를 사람 손으로 1회 확인한다. 브라우저 F5(새로고침)만으로 "됐다" 판정 금지 — 새로고침은 항상 load를 띄워 갱신되므로, 실패하는 유일한 경로(설치형 재개)를 못 잡는다.

  • 새 버전 배포 완료.
  • 설치형 PWA를 폰 최근앱에서 재개(새로고침 X) → 몇 초 내 자동 갱신 확인.
  • iOS Safari 설치본 있으면 동일 재개 확인(가장 취약한 환경).

  • ✅ 직전 동일 기간 대비 증감(▲/▼/–)도 함께 표시합니다.

  • 각 카테고리의 활동 시간이 시간 흐름에 따라 어떻게 변화하는지 시각화합니다. (현재 구현은 회고 점수가 아닌 카테고리별 활동 시간(분) 기준)
  • 상승/하락/정체 추세를 한눈에 파악할 수 있습니다.

2-3. 인사이트

트렌드 데이터에서 도출한 패턴을 자연어로 제시합니다.

  • ✅ 요일별 변동 패턴 (예: "화~목 집중도가 높고 금요일에 급락")
  • ☐ 카테고리 간 상관관계 (예: "운동 점수가 높은 날 업무 집중도도 상승")
  • ✅ 상승/하락 추세 감지 (선형 회귀 기울기 ±0.5 임계)
  • ✅ 미활동 카테고리 경고
  • ✅ 회고 기록률 저하 경고

2-4. 처방전 ✅

종합 점수·트렌드·인사이트를 종합하여 구체적인 행동 방안을 제시합니다.

3. 진단 레벨

몰입 에너지 (Focus Density) ☐

  • 지표: 타이머 작동 시간 vs 휴식 간격.
  • 처방: 순수 활동 시간을 계산하여 현재 유저가 몰입 중인지, 기력이 소진되어 효율이 낮은 상태인지를 시각화합니다.

루틴 일관성 (Routine Consistency) ☐

  • 지표: 활동 시작 시각의 표준 편차 + 주간 실천율 변동성.
  • 처방: 불규칙한 생활 패턴이 효율 저하의 원인인지를 진단합니다.

스윗미 스마트 가이드 (Smart Guidance)

활용정보/유저_공부계획팁.md · 읽는 시점: 가이드·추천 기능 기획 시

이 가이드는 스윗미의 데이터 분석 결과에 따라 사용자가 즉각적으로 실행할 수 있는 생산성 전략을 제공합니다.

1. 패턴 데이터 기반 맞춤형 전략

몰입 밀도 저하 시: 집중 세션 전환

  • 분석 결과: 활동 시간 대비 실질적인 성취감이 낮거나 멍하니 있는 시간이 많을 때.
  • 실행: 현재 카테고리의 활동 방식을 점검하고, 짧고 집중적인 세션(25~30분)으로 전환하세요.

정체기 극복: 카테고리 교차 (Interleaving)

  • 분석 결과: 한 카테고리만 오래 붙잡고 있어 집중 효율이 급격히 떨어지는 시점.
  • 실행: 같은 카테고리만 반복하기보다 성격이 다른 2~3개 카테고리를 섞어서 진행하세요. 뇌의 유연성을 높여 효율을 극대화합니다.

2. 대시보드 데이터 활용 루틴

목표 달성률 최적화

  • Tips: 수립한 계획의 실천율이 70% 미만이라면, 마감일로부터 역순으로 분량을 재조정하세요. 무리한 계획보다 완수 가능한 '작은 성공'의 반복이 중요합니다.

시간 관리의 함정

  • Tips: 타이머 시간만 채우는 비효율적 활동을 주의하세요. 회고에서 집중도와 몰입도를 함께 기록하여, 가장 효율적인 시간대를 찾아내야 합니다.

3. 생산성 최적화 상식

  • 메타인지 강화: 내가 잘하는 것과 부족한 것을 명확히 구분하는 것이 개선의 시작입니다. 회고 점수가 지속적으로 낮은 카테고리를 우선 점검하세요.
  • 환경 변수 통제: 데이터 분석 상 특정 환경이 집중도를 낮추는 패턴이 확인된다면 환경을 조정한 후 집중 모드를 활용하세요.

1. 포지셔닝 — 한 문장 무기 (2026-07-21 재작성)

경쟁 앱(열품타·타임스탬프·투두메이트) 대비 차별점 2개로 좁힌다.

  • "기록만 하는 앱 말고, 처방까지 해주는 앱" — 공부시간 재는 앱은 많다. 스윗미는 데이터를 보고 무엇을 고쳐야 하는지 알려준다 (처방전·인사이트). 변경 없음.
  • "가입 없이 바로 쓰고, 원하면 로그인해서 기기 간 동기화" — 경쟁 앱은 시작부터 가입·친구추가를 요구한다. 스윗미는 게스트로 즉시 시작하고, 로그인은 기기를 옮기거나 데이터를 지키고 싶을 때만 선택한다.

✅ 출시 순서 (2026-07-21 확정, 2026-07-23 근거 일부 변경) — Phase 3 먼저

결정: Phase 3(로그인·동기화·푸시)를 먼저 하고 출시한다. 개인정보처리방침은 처음부터 "수집함" 기준 1회 작성.

⚠️ 전제 변경 (2026-07-23): 이 순서의 1순위 근거였던 "데이터 유실 해소"는 이제 하이브리드 셸이 독립적으로 제공한다(네이티브 저장소, PRD §10-6). 따라서 Phase-3-먼저의 근거는 "방침을 '수집함'으로 1회만 작성(2회 재작성·재제출 회피)"와 정직성으로 이동했다. 데이터 유실 방지는 더 이상 순서를 강제하지 않는다. → 순서를 유지할지 재검토할지는 유저 판단 대상(발견만 기록, 미실행).

⚠️ 순환 의존(불변): "Phase 3 전부 완료 → 출시"는 물리적으로 불가능하다(결제 상품 등록은 스토어에 앱이 생성된 뒤에만 가능). 따라서 Phase 3를 출시 전/후로 쪼갠다. 실행 순서도와 세부 근거는 docs/phase3-할일.md가 단일 출처 — 여기 복제하지 않는다.

기각한 순서 (출시 먼저): 출시가 2~3주 빠르나 방침·데이터 안전 양식을 2회 작성해야 한다. "방침 갱신·재제출 경험"은 출시 후 기능 추가 시 자연히 발생하므로 영구 손실이 아니라 시점 이동이다.

3. 기술 스택 및 구조

프론트엔드 / 백엔드

  • 프론트엔드: HTML5 + Vanilla JS(ES6+) + Vanilla CSS. PWA(vite-plugin-pwa, Service Worker).
  • 앱 셸: ✅ 확정 — 하이브리드(Capacitor). 기존 웹 코드를 네이티브 WebView에 담아 iOS·Android 동시 빌드. 결정 근거·기각안·뒤집힘 조건은 PRD §10.
  • 백엔드: ✅ 확정 — Firebase(BaaS). ✅ 인증(Firebase Auth: 구글+이메일)·DB 동기화(Firestore) 구현 완료(2026-07-26 실검증). ☐ 푸시(FCM)·결제 검증 미착수. Firebase는 iOS·Android SDK를 정식 지원. 결제는 이중 IAP(Google Play Billing + Apple StoreKit). 결정 근거·기각안·뒤집힘 조건은 PRD §9-5.

모듈화 계획 (UI ↔ 비즈니스 로직 분리)

  • 상태 레이어: js/store.js의 state 객체 중앙 관리, 변경 후 saveToLocal() 호출 필수.
  • 로직 레이어: 타이머 로직 js/timer.js 독립. 새 전역 함수는 window 등록 패턴.
  • UI 레이어: PC(#desktop-shell)/모바일(#mobile-shell) 셸 분리. 모바일은 PC 타이머를 MutationObserver로 감시·동기화.

데이터 모델

  • 로컬(1차 저장소, localStorage): 카테고리, 날짜별 할 일/플랜, 타임테이블 history(활동 세션), 회고 점수, 습관(요일·매일 반복), 사탕 잔량.
  • 사용자/계정 데이터: ✅ Firestore 스키마 설계·구현 완료 — 계정별 문서에 위 로컬 데이터를 매핑해 동기화. 게스트 데이터는 분리 보관. 세부 → docs/phase3-할일.md §2.
